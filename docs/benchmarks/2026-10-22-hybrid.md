# Labeled logical-prepass comparison

[Hosted run 39739018058](https://github.com/STEVVVU/sql-query-optimizer/actions/runs/39739018058), source `4fc9ca80955ca58bbf64b123d0625d8becf2e098`, retained artifact `optimizer-hybrid-39739018058`. Its summary SHA256 is `9a06964026a577b6fb5e02c53927e77513345ed8afd08da10a7b9d83659b22fc`. All 270 actions passed ordered-value and physical-output-type parity: 45 groups, each with one excluded warmup and five measured repetitions. The artifact's per-file hashes and completeness were independently checked, the summary was reconstructed from every sample, all 15 sets of retained three-arm output values matched, and each size's process exited zero. Types are asserted by the real Rust consumer during every action; field aliases are outside that assertion.

The three arms are the existing standalone optd logical/Cascades pipeline (`optd`), DataFusion's ordinary optimizer (`datafusion`), and the existing bridge's DataFusion logical prepass followed by optd (`optd_df_logical`). This adds a separately configured optimizer stack; it does not change standalone optd's algorithm. Adaptive and advanced-cost options remain disabled. The original SQL, deterministic fixture, skew, and timers are unchanged: 80% of orders belong to customer zero, four target partitions, batch size 8192, and five queries at 1k/100k/1m orders. Every repetition reverses arm order. Each arm gets a fresh context and the same in-memory seed before timing. Planning covers SQL through physical-plan creation; execution collects the plan. Fixture construction, result conversion/validation and diagnostic formatting are outside the timers. The whole in-memory consumer's planning-plus-execution total is reported; these are not CLI startup or file-I/O timings.

The runner used Ubuntu 24.04, Linux 7.0.0-1017-azure, AMD EPYC 7763, two assigned physical cores/four logical CPUs, and Rust/Cargo 1.99.1 release builds. Every size has a 300-second process bound and the workflow checks a 10GiB disk reserve. No imposed memory limit or spill claim is made. Results below compare arms within this run; the earlier typed baseline used a different host/compiler context and remains a separate record.

The prepass reduces the 1m selective join total median by 43.8% relative to standalone optd. Executed operator metrics show the mechanism: standalone optd probes all 1m orders against one customer, whereas the prepass derives `customer_id=1` and filters orders to 10k before joining. This was also reproduced in the separate setup smoke's executed plan. The benefit does not generalize: the extra planning raises total medians for every other size/query combination in this matrix. Standalone optd retains the lower aggregate time; no overall hybrid optimizer win is claimed.

Root physical statistics are still incomplete and must not be presented as calibrated model estimates. At 1m orders the hybrid selective root estimates 20m rows versus 10k actual (Q-error 2000), matching the DataFusion root estimate. Standalone and hybrid global-aggregate roots expose 1m rows versus one actual (Q-error 1m), while DataFusion reports one. Other roots have absent statistics. Verbose optd internal costs remain separately retained. The logical prepass does not fix the standalone cardinality model or establish skew estimation quality.

GNU-time peak process RSS was 43,448 / 64,596 / 261,248 KiB at 1k / 100k / 1m orders, across all three arms, all queries and fixture construction; it cannot be attributed to an individual optimizer. No swaps or major page faults were recorded. The 1m process used 2.17s user and 0.20s system CPU, with 1.84s whole-process wall time including setup/diagnostics.
